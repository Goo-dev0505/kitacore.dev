PART 01 / COMMON

みんな読むやつ、
根本の話。

普段使い派も実装派も、ここだけは共通の前提や。 ここ押さえとけば、あとの応用は枝葉の話やと思うてくれてええ。

01.

ベテランに頼む感じが、
新しい正解やで。

これまでのAI（GPT-5.4まで）はな、新人さんに仕事を頼む感じやってん。 迷子にならんように、手順を細かく書いてあげる必要があったわけや。

▮ TATOERU NARA / たとえると

新人さんに「コピー10部とって、ホチキスは左上で、机Aに置いて」って手順全部書くのがいままで。

ベテランに「会議用に資料配れる状態にしといて」って結果だけ頼むのがこれから。

GPT-5.5 はかなりベテラン寄りになったんよ。 やから「まずA、次にB、最後にC」みたいに細かく書くと、むしろ動きがガチガチになって機械的な答えが返ってくるねん。

大事なんは 「結果」を伝えること。 何ができてればOKか、何があってほしいか。それだけや。

02.

5.4 → 5.5で
変わった4つのこと。

  • 01
    古いプロンプトをそのまま持ってきたら劣化する 「ALWAYS〜」「NEVER〜」「まずA、次にB…」みたいな指示が、5.5 ではノイズになって動きが機械的になるねん。最小のプロンプトから書き直すのが推奨や。
  • 02
    考える深さの初期設定が medium になった 5.4 までは none（考えん）が既定。5.5 は medium が既定や。低レベルでも賢う動くから、まず low や medium で試して、足りなんだら上げる。これが基本動作やで。
  • 03
    デフォルトのトーンが「効率重視・直接的」 そっけない感じすらある、っちゅうくらい簡潔。お客さん向けや温かみが必要な用途では、人格設定を明示的に書かなアカン。
  • 04
    長時間タスク・ツール多用は preamble と phase が引き続き効く これは 5.4 から続く話。考え込んでる間に「ちょっと待ってくれ感」を出すには preamble、中間更新と最終回答の区別には phase。詳しいのは DEEP MODE で。
▮ ここポイントやで
「必ず（ALWAYS）」「絶対に〜するな（NEVER）」は、ホンマに絶対の時だけ

プライバシー、安全、絶対に間違えたらアカンルール。これだけが「絶対」や。

「いつ調べるか」「どの順でやるか」みたいな 判断系 を全部「必ず〜」で縛ったら、AI が融通きかんくなって出力がショボくなるで。

PART 02 / EASY MODE

普段使い派の
あんたへ。

ChatGPT を普通に使うてる人向け。日常の例とたとえ話だけで進めるで。 実装の話は出てけぇへんから安心してや。

03.

残念な頼み方
vs ええ頼み方。

具体例で見るのがいちばん早いわ。 左の「残念」は、ついやってまうやつ。右の「ええ」は、5.5 で結果が良くなる書き方や。

PATTERN 01 / 明日の天気を聞きたい

残念
手順を全部書いてまう
明日の天気について、まず気象庁のサイトを見て、それから関連ニュースも確認して、温度と湿度と降水確率を調べて、過去のデータも比較して、表でまとめて、最後に服装のアドバイスもつけてください。

→ 手順多すぎて、全部きっちりやろうとして長くて固い答えになるねん。

ええ
ゴールと長さだけ
明日の東京の天気をふまえて、何を着ていけばええか教えて。
理由もちょっと添えて、3行くらいで。

→ ゴール（着るもの）と長さ（3行）だけ伝える。調べ方は AI が選んでくれるで。

PATTERN 02 / 文章を直してほしい

残念
全部直してと頼む
以下の文章を、まず誤字を直して、それから言い回しをチェックして、それから論理構成も見直して、それから読みやすくして、それから敬語も確認して…

→ 全部やろうとして、勝手に大改修されることが多いんよ。

ええ
変えてええ部分を限定する
この文章を、長さや構成は変えずに、読みやすさだけ整えて。
新しい主張を足したり、宣伝っぽくしたりせんといて。

→ 「変えてええ部分」と「変えたらアカン部分」を先に伝える。これだけで暴走せえへん。

PATTERN 03 / 旅行プランを立てたい

残念
「必ず」を連発する
京都の旅行プランを作って。必ず観光地を10個入れて、必ず食事処も入れて、必ず移動時間も書いて、必ず予算も入れて、必ず…

→ 「必ず」が多すぎて、ぎゅうぎゅう詰めの使えんプランになるねん。

ええ
状況と判断軸を渡す
京都に1泊2日で行くねん。歩くの好き、人混み苦手、予算は1人3万円。
無理のないプラン作って。足りん情報があったら聞いてや。

→ 自分の状況と判断軸を渡す。あとは AI が選ぶ。「足りん情報は聞いて」も大事や。

04.

声色（こわいろ）を
決めたって。

GPT-5.5 のデフォルトはちょっと そっけない ねん。 「効率重視・直接・タスク志向」がデフォ。仕事には便利やけど、相談ごとや日常チャットやと冷たく感じることもあるわ。

対策はかんたん。「どんな人として話してほしいか」を最初に書く。それだけや。

YOU

あなたは丁寧で穏やかな、頼れる先輩のように話してください。専門用語は使わず、たとえ話で説明して。

では質問です。○○について教えてください。

AI

はい、お聞きしますね。○○というのは、たとえると...

これだけで、グッと温かみが出るで。 最初の数行で「人格設定」しとくのがコツや。ChatGPT の「カスタム指示」に書いとけば、毎回書かんでええで。

▮ ここポイントやで
声色は「体験」を整える道具。中身の代わりにはせえへんこと

やさしいトーンで頼んだからって、目的・条件があいまいなままやったら、結果は雰囲気だけの使えん答えになるで。 まず 何をしてほしいか。次に どんなトーンで。順番が大事やねん。

05.

「ちょっと待ってな」を
言わせるねん。

AI に難しい質問投げると、考え込んで 最初の文字が出るまで時間かかる ことがあるねん。 その間ユーザーは「壊れた？」って不安になりがちやろ。

1–2
最初に出してほしい「お返事」の長さは、1〜2文。 長すぎたら邪魔。短い「了解です、まず○○から見ますね」だけで体感速度がグンと上がるで。
指示

時間のかかる作業を始めるときは、まず1〜2文で「了解しました、最初に○○から始めます」と簡単に教えてから作業を始めてください。

▮ TATOERU NARA / たとえると

レジで店員さんが何も言わんと作業始めると、ちょっと不安なるやろ。

「お会計108円ですね、お預かりします」って 一言あるだけで、同じ時間でも「ちゃんと進んでる」って安心するやん。その一言を AI にも言うてもらうイメージや。

06.

「いつ止まるか」を
教えたって。

AI は「もっとちゃんとやろう」と思って 調べすぎる ことがあるねん。 検索しまくったり、確認しまくったり、長い長い回答書いたり…。

これを防ぐには、「いつ止まってええか」 を伝えるんや。

指示

ちゃんとした答えを出すのに必要な分だけ調べて、すぐに答えて。
わからない部分があったら、深追いせずに「ここは不明です」とそのまま書いて。

▮ ここポイントやで
「念入りに調べてから答えて」が古い正解、「最小限の証拠で答えて止まる」が新しい正解や

昔は「とにかく丁寧に調べて」が安全策やってん。 でも GPT-5.5 では 必要十分な情報で答えてサッと止まる 方が、結果の質も体感速度もええ傾向あるねん。集めすぎが偉い、ちゃうんよ。

07.

そのまま使える、
かんたんテンプレ。

ここまでの話を、ひとつのテンプレにまとめたで。必要な行だけ 使うたらええ。 「ゴール」と「条件」だけでも、いままでのダラダラ指示よりずっと結果が良くなるで。

EASY PROMPT TEMPLATE / 普段使い向けテンプレ
役割 あなたは○○です。 例：丁寧で頼れる編集者です
声色 ○○のトーンで話してください。 例：やさしく、でも甘くなく。専門用語は使わず
ゴール 最終的に○○ができている状態にしてください。 例：800字程度のブログ記事の冒頭
条件 ○○は守って、○○は変えないで。 例：固有名詞は変えない／宣伝っぽくしない
長さ・形 ○○の長さで、○○の形式で。 例：3段落、見出しなしのプレーン文章
止め時 ○○ができたら止まって。 例：足りない情報があれば質問して止まる

PART 03 / DEEP MODE

実装・本格派の
あんたへ。

note で活用したり、業務に組み込んだり、API でアプリ作ったりする人向け。 ここからは XML タグつきテンプレや API パラメータの話も出てくるで。

08.

アウトカム重視で
構造化するんや。

EASY MODE の「ゴール伝える」を、もっと厳密に書くとこうなるねん。 4つの要素を意識すると、プロンプトの安定性がガッと上がるで。

要素何を書くか例
Goalユーザーに見せる最終結果顧客の問い合わせを解決する
Success criteria「これが揃ってたら完了」の定義判定済み・アクション完了・必要フィールド含む
Constraints守るべきルール（安全・予算・形式）個人情報を要約に含めへん
Stop rulesいつやめるか・いつ諦めるか必要な証拠が揃ったら回答して止まる

原文の推奨例（公式そのまま）

Resolve the customer's issue end to end. Success means: - the eligibility decision is made from the available policy and account data - any allowed action is completed before responding - the final answer includes completed_actions, customer_message, and blockers - if evidence is missing, ask for the smallest missing field

「ALWAYS / NEVER」の使い分け

安全ルール、必須出力フィールド、絶対やったらアカン操作。これらは ALWAYS / NEVER でええ。 でも判断系（いつ検索するか、いつ確認するか）を強い言葉で縛ると、5.5 では検索空間が狭まって出力が劣化するんよ。 判断系は「○○の時は△△する」っていうルールの形で書こうな。

09.

パーソナリティと
コラボスタイルは分ける。

公式の推奨は パーソナリティ（声・トーン）と コラボスタイル（仕事の進め方）を分けて書くこと。 それぞれ短く、目的・成功条件・制約の代わりにせえへんこと。

公式例：落ち着いたタスク重視タイプ

# Personality You are a capable collaborator: approachable, steady, and direct. Assume the user is competent and acting in good faith, and respond with patience, respect, and practical helpfulness. Prefer making progress over stopping for clarification when the request is already clear enough to attempt. Use context and reasonable assumptions to move forward. Ask for clarification only when the missing information would materially change the answer or create meaningful risk, and keep any question narrow. Stay concise without becoming curt. Give enough context for the user to understand and trust the answer, then stop. Use examples, comparisons, or simple analogies when they make the point easier to grasp. When correcting the user or disagreeing, be candid but constructive. When an error is pointed out, acknowledge it plainly and focus on fixing it. Match the user's tone within professional bounds. Avoid emojis and profanity by default, unless the user explicitly asks for that style.

プリアンブル（時間稼ぎの一言）

ストリーミング応答で「最初の文字までの時間」を改善するパターンや。 ツール多用・長時間ワークフローでは特に効くで。

Before any tool calls for a multi-step task, send a short user-visible update that acknowledges the request and states the first step. Keep it to one or two sentences.

コーディングエージェント向けはもっと明示的にいこか：

You must always start with an intermediary update before any content in the analysis channel if the task will require calling tools. The user update should acknowledge the request and explain your first step.
10.

検索バジェット・引用・
創作ガード。

事実ベースの回答作る時は、「何を調べるか」「どこまで調べるか」「足りなんだらどうするか」の3つを書くねん。 RAG使うてる人は特に重要や。

検索バジェット：いつ検索やめるか

For ordinary Q&A, start with one broad search using short, discriminative keywords. If the top results contain enough citable support for the core request, answer from those results instead of searching again. Make another retrieval call only when: - The top results do not answer the core question. - A required fact, parameter, owner, date, ID, or source is missing. - The user asked for exhaustive coverage, a comparison, or a list. - A specific document, URL, email, meeting, record, or code artifact must be read. - The answer would otherwise contain an important unsupported claim. Do not search again to improve phrasing, add examples, cite nonessential details, or support wording that can safely be made more generic.

創作ガード：事実と創作の境界線

スライド・営業コピー・要約を AI に作らせる時、引用すべき事実と言葉で繕ってええ部分を区別させるんや。 これがないと、AI が「導入企業 前年比132%成長」みたいな 誰も言うてない数字 を作文してくることがあるで。怖いやろ。

For creative or generative requests such as slides, leadership blurbs, outbound copy, summaries for sharing, talk tracks, or narrative framing, distinguish source-backed facts from creative wording. - Use retrieved or provided facts for concrete product, customer, metric, roadmap, date, capability, and competitive claims, and cite those claims. - Do not invent specific names, first-party data claims, metrics, roadmap status, customer outcomes, or product capabilities to make the draft sound stronger. - If there is little or no citable support, write a useful generic draft with placeholders or clearly labeled assumptions rather than unsupported specifics.
11.

自己検証ループと
phaseパラメータ。

コーディングエージェントの自己検証

ツールが使える環境では、AI に自分の出力をチェックさせるんや。

After making changes, run the most relevant validation available: - targeted unit tests for changed behavior - type checks or lint checks when applicable - build checks for affected packages - a minimal smoke test when full validation is too expensive If validation cannot be run, explain why and describe the next best check.

UI生成：レンダリング後の確認まで

Render the artifact before finalizing. Inspect the rendered output for layout, clipping, spacing, missing content, and visual consistency. Revise until the rendered output matches the requirements.

phase パラメータ（API向け）

長時間処理で 中間メッセージ と 最終回答 を区別するためのパラメータや。 これがないと、preamble が「もう答え出た」と誤認されることがあるで。

phase 値意味使う場所
commentary中間更新（preamble・進捗）ツール呼ぶ前の説明とか
final_answer完成した最終回答ホンマの答え
If manually replaying assistant items: - Preserve assistant `phase` values exactly. - Use `phase: "commentary"` for intermediate user-visible updates. - Use `phase: "final_answer"` for the completed answer. - Do not add `phase` to user messages.
▮ ここポイントやで
previous_response_id 使うてれば自動で済むで

Responses API で previous_response_id 渡してる場合は、phase の保存は API 側がやってくれるねん。 自分で履歴を組み立て直す時だけ、phase を維持する必要があるんよ。

12.

推奨プロンプト構造
（DEEP用フルテンプレ）。

公式が推奨する完全な構造や。複雑なシステムプロンプト書く時の出発点として使えるで。 各セクションは短く、必要な行だけ。

Role: [1-2 sentences defining the model's function, context, and job] # Personality [tone, demeanor, and collaboration style] # Goal [user-visible outcome] # Success criteria [what must be true before the final answer] # Constraints [policy, safety, business, evidence, and side-effect limits] # Output [sections, length, and tone] # Stop rules [when to retry, fallback, abstain, ask, or stop]

reasoning_effort の使い分け

Effort使いどころ
lowレイテンシ重視。チャット、短い構造化変換、トリアージ
medium（既定）多くのケース。リサーチ寄り、長文合成、矛盾解決
highmedium で足りん高難度推論
xhigheval で明確な利益が出た時だけ。長時間エージェント向け

重要なんは 「higher = better」とちゃう っちゅうこと。 effort 上げる前に completeness_contract・verification_loop・tool_persistence_rules 追加するほうが効くケースが多いねん。

移行チェックリスト。

  • 古いプロンプトを fresh baseline で書き直した（drop-in 移行を避けた）

14.

よくある質問。

これまでの古いプロンプト、もう使えへんの？

使えるけど、答えがカチコチで機械的になりがちや。

特に「ALWAYS〜」「NEVER〜」「まず〜、次に〜」みたいな指示が多い場合、書き直した方が結果ようなるで。一気に全部やらんと、よう使うプロンプトから順番にな。

日本語で書いてもええんか？

OKやで。普通のチャット使う分には日本語で全然いける。

ただ、開発者がアプリ作る時の「システム設定」の部分は、英語のほうが安定する傾向あるねん。これは普通の人は気にせんでええ。

短くしすぎて、AI がちゃんと理解せえへんかったら？

短い指示で1回試してみて、思った答えが出てこんかったら 足りん部分だけ 補足してや。

いきなり全部書くより、「短く頼む → 補足する」のほうが、結果的に短くて的確なプロンプトに育っていくで。

声色決めると、毎回同じ前置き書かなアカン？

ChatGPT のメモリ機能やカスタム指示（Custom Instructions）に書いとけば、毎回書かんでええ。

「私は普段こういうトーンで答えてほしい」って一度設定しとけば、以降は自動で適用されるで。

「考える深さ（reasoning_effort）」って気にせなアカンの？

ふつうに ChatGPT 使うてる人は気にせんでええ。AI 側で勝手に調整されるねん。

API でアプリ作る人だけ、reasoning_effort という設定で「low / medium / high / xhigh」を選べる。GPT-5.5 は medium が標準。多くの場合 low か medium で十分や。

5.4 から 5.5 へ、プロンプトそのまま移行してええ？

公式は 「drop-in migration やのうて、fresh baseline で書き直せ」 って強く推奨してるで。

5.4 までのプロンプトは「過去の弱点をカバーするための回避策」が積み上がってるから、5.5 では ノイズ になって出力が機械的になるんよ。よく使うプロンプトから順に、最小構成で書き直すのがオススメや。

結局、何から始めたらええ？

いつもよう使うプロンプトを1つ選んで、「ゴールだけ書く」 に書き直してみてや。

「まず○○、次に○○」を全部消して、「最終的に○○ができてればOK」っていう1〜2文だけにする。これがいちばん効くで。

REMEMBER / おさらい

こまかく指示するの、やめや。
ゴールと条件だけ、伝えや。
止まる場所も、教えたって。

この3つ覚えとけば、GPT-5.5 はだいたいうまく動くで。 迷ったら、最初の3行に「何ができてほしいか」だけ書いて投げてみい。
